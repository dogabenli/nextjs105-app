# Sitecore Personalize POC testing

## Purpose

This runbook verifies that a standalone Sitecore Personalize web experience can personalize the `ContentBlock` component on a Sitecore JSS Next.js page while the original page remains compatible with SSG/ISR.

The test page is:

```text
/personalize-demo
```

The original heading and description come from Sitecore. After the page loads, Sitecore Personalize changes those values in the browser for the selected experience variant.

## Prerequisites

Before testing, confirm that:

- The Personalize experience is saved in Draft state.
- The experience uses the Point of Sale `jss-poc-web`.
- The application is running on port `3000`.
- `@sitecore/engage` initializes with `webPersonalization: true`.
- The client key and US target URL are configured.
- Local cookie configuration uses `localhost`:

```env
NEXT_PUBLIC_PERSONALIZE_COOKIE_DOMAIN=localhost
NEXT_PUBLIC_PERSONALIZE_TARGET_URL=https://api-engage-us.sitecorecloud.io
```

If a `NEXT_PUBLIC_*` setting changes, restart `npm run dev`. When testing with `npm start`, run a new production build before restarting because public environment variables are embedded during the build.

## Page targeting

Use the following case-insensitive regular expression so the experience accepts the local hosts and the Personalize QA query parameters:

```regex
^https?://(?:localhost|127\.0\.0\.1|(?:en|da)\.nextjs105\.local):3000/personalize-demo/?(?:[?#].*)?$
```

Also restrict the experience to the Point of Sale:

```text
jss-poc-web
```

## Variant configuration

The POC variant targets the existing ContentBlock markup. The component must render the expected selectors, for example:

```text
.contentBlock
.contentTitle
.contentDescription
```

Example variant JavaScript:

```javascript
const component = document.querySelector('.contentBlock');

if (component) {
  const title = component.querySelector('.contentTitle');
  const description = component.querySelector('.contentDescription');

  if (title) {
    title.textContent = 'Personalized title';
  }

  if (description) {
    description.innerHTML =
      '<p>This content was delivered by Sitecore Personalize.</p>';
  }
}
```

For temporary diagnostics, add the following at the start of the variant JavaScript:

```javascript
console.log('[Personalize] ContentBlock variant executed');
```

## Local testing procedure

### 1. Verify the original page

Open:

```text
http://localhost:3000/personalize-demo
```

Confirm that:

- The page returns HTTP 200.
- The original ContentBlock heading and description from Sitecore are visible.
- No personalized variant content is present in the original server-generated HTML.

### 2. Grant POC consent

There is no consent manager in this POC. In the browser console on the same origin used for the test, run:

```javascript
localStorage.setItem('personalize-demo-consent', 'granted');
window.dispatchEvent(new Event('personalize-consent-change'));
```

Reload the page after granting consent if initialization does not start immediately.

Consent is stored per browser origin. Consent granted on `localhost` is not available on `127.0.0.1`, and the reverse is also true.

### 3. Verify initialization and event collection

In DevTools, open the Network and Application panels. Confirm:

| Check | Expected result |
| --- | --- |
| `browser/create.json` | HTTP 201 |
| VIEW request to `/v1.2/events` | HTTP 201 |
| `bid_*` cookie | Present for `localhost` |
| Personalize session cookies | Present |
| Event Viewer | VIEW event appears for `jss-poc-web` |

Do not manually create or copy a `bid_*` cookie. The browser ID must be generated by the Personalize tenant.

### 4. Start Personalize Preview

The Personalize Preview dialog rejects `localhost` but accepts the loopback IP. Enter:

```text
http://127.0.0.1:3000/personalize-demo
```

Click **Preview**. Personalize opens a URL similar to:

```text
http://127.0.0.1:3000/personalize-demo?bxQATool=true&bxFlowRef=...
```

### 5. Switch the Preview URL to localhost

The Engage SDK local cookie configuration supports `localhost`. After the Preview page opens, preserve the complete path and query string but replace only the hostname:

```text
http://localhost:3000/personalize-demo?bxQATool=true&bxFlowRef=...
```

Do not remove `bxQATool`, `bxFlowRef`, or other parameters added by Personalize.

If necessary, grant consent again on `localhost` using the commands in step 2, then reload the same QA URL.

### 6. Select and verify the variant

In the Personalize QA tool, select the personalized variant rather than the control/original variant.

Confirm that:

- The heading changes to the configured personalized heading.
- The description changes to the configured personalized description.
- The variant diagnostic message appears in the console, if enabled.
- The VIEW event returns HTTP 201.
- The hosted personalization request returns HTTP 200.

## Expected result

The completed test demonstrates that:

1. Sitecore supplies and statically renders the original page and ContentBlock data.
2. The public page remains suitable for SSG/ISR and can be shared by all visitors.
3. After consent, Engage identifies the browser and sends behavioral events.
4. Sitecore Personalize evaluates the visitor and page in the browser.
5. Personalize changes only the selected component after page load.
6. Personalized content is not stored in the shared static page output.

## Troubleshooting

### No Personalize cookies

- Confirm consent was granted on the current origin.
- Confirm `NEXT_PUBLIC_PERSONALIZE_COOKIE_DOMAIN=localhost`.
- Clear site data for `localhost`, grant consent again, and reload.
- Do not use `127.0.0.1` as the final Engage cookie domain for this POC.

### Event returns `Invalid browser id/ref specified`

Clear the `bid_*` and Personalize session cookies, then allow the SDK to request a new browser ID. Do not reuse a browser ID created for another origin, tenant, client key, or environment.

### Preview opens but Sitecore content does not change

Check the following in order:

1. The final URL uses `localhost` and retains the QA query parameters.
2. The personalized variant, not the control variant, is selected.
3. The VIEW event returns HTTP 201.
4. `document.querySelector('.contentBlock')` returns the component element.
5. The browser console contains no variant JavaScript errors.
6. The variant was saved before generating the Preview link.

### Variant code works manually but not through Personalize

Add a diagnostic `console.log` as the first statement of the variant. If it does not appear, the variant was not delivered or executed. Recheck the page-targeting rule, Point of Sale, QA parameters, selected variant, VIEW event, and hosted personalization request.

## Cleanup

After testing:

- Remove temporary diagnostic logging from the variant.
- Keep the experience in Draft unless a controlled live test is required.
- Optionally revoke the local POC consent:

```javascript
localStorage.removeItem('personalize-demo-consent');
window.dispatchEvent(new Event('personalize-consent-change'));
```
